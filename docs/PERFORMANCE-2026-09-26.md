# 2026-09-26 本地流畅度优化记录

本次针对“点了以后要等、切换分析条件不够顺畅”进行优化。没有删除公式、缩短用户选择的期数，也没有改变任何公式计算规则。

## 核心调整

- 历史计算常驻后台，不再每换一页就销毁全部结果。
- 默认只向页面传递逐期结果、命中状态等必要历史；重复的号码数组和开奖属性共用一份。完整变量、表达式和运算过程仍保留在后台，查看指定公式或完整导出时取回。
- 计算缓存按真正影响结果的公式、开奖属性和配置区分。改名称、人工确认或加入/退出综合参考，不再重新计算全部公式；返回结果会补上最新名称和状态。
- 修改一条公式时，其他未变公式的历史结果可以复用。开奖数据或历史属性变化会使旧数学缓存失效，避免沿用旧结果。
- 分析页保持一个后台线程；不同动作、结果类型共享相同的公式结果和健康指标。期数变化复用基础历史计算，再按所选范围整理。
- 异常时给出可重试提示，不再把后台失败的重计算转回页面线程，避免页面突然卡住。
- 快速切换条件或离开页面时，旧请求不会覆盖新请求。完整导出与指定公式明细有独立的完整数据路径。

## 指示性测量

测试数据是项目现有静态快照：212 期开奖、258 条公式，其中 253 条启用，共 53,382 条历史明细。在同一台电脑中用 Node 单次测量：

| 项目 | 原完整结果 | 默认紧凑结果 |
| --- | ---: | ---: |
| JSON 序列化体积 | 68,166,814 字节 | 5,263,826 字节 |
| 对象复制时间 | 约 241 毫秒 | 约 75 毫秒 |
| 打包 / 解包 | 无 | 约 7 / 18 毫秒 |

默认传递的序列化体积减少约 92.3%。同次测量首次计算约 802 毫秒，仅改参与状态后复用结果约 1 毫秒。

这些数字用于比较计算和数据传递方式，不是浏览器实际交互耗时，也不是网络下载量；不同设备、数据量和运行模式下会有变化。生产预览与浏览器交互验收由主任务另行进行。

## 保真与异常检查

针对性测试核对以下事项：所有逐期原始值、归位结果、映射结果、开奖属性、未来期验证、命中状态、落点趋势和同条件比较保持一致；指定公式完整计算过程与原结果一致；完整导出不丢任何明细；改名及时反映；真正改公式或历史属性时正确失效；旧请求和故障线程不能污染新结果。

首轮针对性测试 5 个文件、44 项通过，类型检查通过。最终全套检查与集成验收以主任务完成时的结果为准。

## 仍需明确的边界

- 第一次计算全部历史仍需计算时间；优化主要减少重复计算、复制和页面阻塞。
- 完整导出主动取回全部计算过程，数据量仍大，这是保持完整性的必要成本。
- 默认紧凑历史不包含运算过程，任何新增需要展示过程或完整导出的入口都必须使用 `detailRuleIds` 或 `fullDetails` 请求。
- 历史数据变动会重建该数据版本的计算；本次没有冒险引入可能漏算跨期公式的“只追加一天”算法。
