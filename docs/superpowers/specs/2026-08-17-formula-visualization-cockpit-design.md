# 公式结果统计分析驾驶舱设计

## 背景与目标

现有“公式结果统计”已经能按结果、期次和公式来源联动，但可视化仍存在几处会影响判断的问题：多结果徽标被压成竖排；展开明细信息密度低且留白过大；环图只画前六项却没有明确“其他”，容易被理解为完整构成；帕累托只有累计百分比数字，没有累计曲线；热图按每一行单独归一化，颜色无法跨期比较；手机端先展示长排行，主趋势被推到首屏之后。

本次目标是在不改变 RuleQuant 现有页面结构、数据口径、iOS 玻璃语言和每日实时更新方式的前提下，把二级可视化升级为商业级分析驾驶舱，并修复截图中的协调性问题。桌面与手机端必须是同一分析逻辑的两个兄弟布局。

## 用户授权与概念状态

- 2026-08-17，用户明确要求“好，你自己一次性完成”和“自己挑一个最好的执行”。
- 批准范围：由 Codex 在候选方向中选择最优方案，并完成设计、实现、验证和发布。
- 选择结果：采用方案 A“分析驾驶舱”。
- Codex 图像概念生成连续两次因网络错误失败；没有将失败图像作为设计依据。
- 替代概念基准：视觉伴侣页面 `analytics-cockpit-selected.html`，以及本文件的桌面/手机语义设计合同。
- 图像概念失败不改变证据锁、阅读顺序、数据绑定、交互和移动端合同；所有图表和文字仍由真实代码与实时数据生成。

## 方案比较

### A. 分析驾驶舱（采用）

保留现有产品语言，按“洞察 → 比较 → 变化 → 原因 → 证据”组织信息。增加趋势比较、排名轨迹、真实帕累托和全局色阶热图，删除分析价值弱且容易误解的半截环图。

优点：分析问题清楚、联动完整、可追溯、符合 Power BI 类商业分析的工作方式。代价：需要重构现有可视化组件并补充数据派生函数和测试。

### B. 图表画廊

保留环图并加入更多雷达、仪表等图形。优点是视觉种类多；缺点是重复编码多、解读负担高，也更容易偏离统计目标，因此不采用。

### C. 紧凑审计面板

仅修复徽标、明细和现有图表。优点是改动小；缺点是无法达到用户要求的商业级分析深度，因此不采用。

## 证据锁

- 分析问题：某一类公式结果在最近十期出现多少次、是否增强、排名如何变化、由哪些公式贡献。
- 统计单位：每条公式对每个唯一结果在每个计算期只计 1 次。
- 时间范围：默认最近十个计算期；期次筛选后所有 KPI、图表和明细使用同一范围。
- 数据来源：现有开奖、公式和实时汇总结果；不创建会过期的独立统计副本。
- 排除与支持使用同一结构但不同语义色；单双、大小继续不纳入统计。
- 半头、半波、门数等现有受支持类型继续参与。
- 任何图表不得改变计数、排序、去重、期次对应或结果名称。

## 阅读路径与信息架构

### 桌面端

1. 固定工具栏：标题、统计范围、实时来源和关闭操作。
2. 自动洞察：用一句可核验的话说明所选结果的最新值、相对十期均值和趋势方向。
3. 主指标：一个主结果指标加三个从属指标，避免所有 KPI 同权。
4. 完整排行 + 趋势比较：左侧精确排行；右侧比较所选结果、当前领先结果和类别中位数。
5. 排名轨迹 + 帕累托：前六结果最近十期的排名变化；公式贡献柱与累计占比曲线。
6. 全局热图：期次 × 结果，所有单元格共用一个色阶，并显示低到高图例。
7. 公式明细：结果芯片、公式信息卡和编号计算步骤。

### 手机端

1. 首屏先显示洞察、主指标和趋势比较。
2. 完整排行改为随后出现的紧凑列表，不再把趋势推到首屏之后。
3. 排名轨迹、帕累托按单列显示；必要时减少直接标签但保留所选结果和端点值。
4. 热图保留横向滚动和固定期次列，滚动条不遮挡数据。
5. 明细结果芯片横排换行，绝不逐字竖排；展开后按卡片和步骤列表组织。

## 交互合同

- 默认状态：沿用主页面当前动作、类型和结果选择；二级窗口默认查看最近十期。
- 选择结果：排行、趋势、排名轨迹、帕累托、热图和明细同步更新。
- 选择期次：KPI、趋势高亮、帕累托、热图和明细同步收窄；提供明显的清除筛选按钮。
- 悬停只提供预览；所有关键值必须在没有悬停时可见。
- 手机端用点击/聚焦替代悬停，主要触控目标不小于 44 CSS px。
- Escape、背景关闭、关闭按钮和焦点回归继续保持；焦点不能逃出模态窗。
- `prefers-reduced-motion` 时取消入场和图表过渡；数据含义不依赖动画。
- 视图选择保持为临时分析状态，关闭窗口后不持久化。原因是数据每日变化，持久化旧的期次和排名会产生误导；主页面的动作/类型/结果仍为当前会话的规范状态。

## 数据派生与架构

- React 负责模态结构、筛选状态、焦点管理和面板布局。
- 纯 TypeScript 函数负责：期次计数矩阵、类别中位数、领先结果序列、并列排名、趋势洞察、帕累托累计占比和全局热图色阶。
- SVG 只负责趋势、排名轨迹和帕累托的真实数据标记；DOM 负责排行、热图和明细，便于可访问性和响应式布局。
- 不新增图表依赖，不引入 WebGL、Canvas 或 3D；当前数据规模不足以证明这些成本有分析价值。
- 同时只存在一个可视化模态窗，约 3 个 SVG 图层、最多 60 个热图单元和一份按需可见的明细列表。
- 组件继续动态加载；昂贵派生使用 `useMemo`；明细继续使用 `content-visibility`，避免首次布局全部展开。

## 实时、失败与空状态

- 数据模型是每日/开奖后快照刷新，不是高频流；窗口显示最新计算期和来源状态。
- 数据刷新失败时保留主页面最后一次可用数据及现有错误提示，不把图表清空成白屏。
- 无结果时显示说明性空状态，不渲染零尺寸 SVG。
- 单一期次时隐藏排名轨迹和趋势比较的无意义部分，改为本期精确比较。
- 公式过程缺失时仍显示公式、表达式和受影响结果，不显示空的步骤区域。

## 颜色与字体合同

- 中性上下文：现有灰蓝文字、边界和分组背景。
- 主要焦点：现有蓝色强调。
- 排除指标：现有 rose/red，只表示排除，不兼作普通分类色。
- 比较线：青色或中性虚线，与所选线同时用线型/标签区分，不能只靠颜色。
- 选中、聚焦和提醒使用不同边框/底色/线型，检查灰阶和色弱辨识。
- 字体继续使用现有 `--font-sans` 与 `--font-mono`，以系统苹方/等价中文字体优先；字号按现有产品层级，不下载或分发受限制的苹方文件。

## 测试与验收

1. 单元测试：中位数、排名轨迹、并列排序、洞察文本、帕累托累计和热图全局最大值。
2. 组件测试：打开/关闭、焦点锁、结果联动、期次联动、清除筛选、空状态和明细展开。
3. 浏览器验收：桌面、390px 手机、浅色、深色、长结果、多结果、长公式过程。
4. 可视检查：无竖排芯片、无横向页面溢出、无嵌套滚动陷阱、首屏主趋势可见、热图图例与色阶一致。
5. 工程验证：完整测试、类型检查、lint、生产构建、静态构建、关键 API/页面和控制台。
6. 发布验证：GitHub 源码分支/PR、CI、GitHub Pages 构建和线上页面均使用同一已验证提交。

## 非目标

- 不增加单双、大小统计。
- 不改变公式计算规则或开奖数据同步逻辑。
- 不加入 3D、粒子、雷达、仪表盘装饰或与证据无关的动画。
- 不使用 Vercel；本次发布目标是用户现有公开 GitHub 仓库和 GitHub Pages 流程。
