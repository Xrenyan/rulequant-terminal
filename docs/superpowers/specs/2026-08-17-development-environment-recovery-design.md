# RuleQuant 开发环境与双平台发布恢复设计

## 背景

RuleQuant 已从旧电脑迁移到 `D:\rulequant-terminal`。迁移包完整保留了业务源码、测试、静态数据、静态构建产物和旧浏览器测试输出，但没有迁移可重建的根目录开发配置、Git 元数据及完整依赖链接。

项目以前已经发布到用户的 GitHub。目标是在不覆盖迁移源码和业务数据的前提下，恢复本地开发能力，并让同一个公开 GitHub 仓库同时支持 GitHub Pages 与 Vercel 发布。

## 目标

1. 以 D 盘迁移项目作为本地唯一工作目录。
2. 恢复可重复安装的 Node.js/pnpm 开发环境。
3. 恢复测试、类型检查和生产构建能力。
4. 识别并接回以前的 GitHub 仓库及历史。
5. 使用同一源码仓库发布 GitHub Pages 静态版本和 Vercel 完整版本。
6. 确保公开仓库不提交本地缓存、浏览器配置或真实密钥。

## 非目标

- 本阶段不重写业务算法或页面交互。
- 不删除原压缩包、`output` 浏览器产物或现有 `out` 静态成品。
- 不在验证完成前覆盖远端默认分支或生产部署。
- 不把客户端访问口令描述为真正的权限控制。

## 恢复策略

采用“旧 GitHub 仓库提供配置依据，D 盘迁移内容提供业务主体”的合并策略。旧项目实际使用两个仓库：`rulequant-terminal` 保存源码并连接 Vercel，`rulequant-terminal-pages` 保存静态构建产物并维持既有 Pages 地址。

1. 安装 GitHub CLI，并由用户完成 GitHub 授权。
2. 定位以前的 RuleQuant 仓库，读取默认分支、历史配置和发布工作流。
3. 将远端仓库接入本地时先比较，不直接覆盖 `src`、`tests`、`scripts`、`public` 或现有数据。
4. 优先从旧仓库恢复根目录配置；旧仓库没有的配置再根据现有源码、pnpm 缓存和框架版本重建。
5. 对有冲突的业务文件保留迁移版本，并单独记录差异后再决定是否合并远端改动。

## 本地开发环境

恢复范围包括：

- `package.json` 与 pnpm 锁文件；
- TypeScript、Next.js、PostCSS/Tailwind 和测试配置；
- `.gitignore`、环境变量示例和项目 README；
- 源码引用的 `data` 目录；
- Node.js 与 pnpm 版本约束；
- 常用脚本：开发、测试、类型检查、构建、静态导出。

依赖版本优先以旧 GitHub 锁文件为准；如果旧仓库不可用，则依据迁移包中的 pnpm 存储恢复与 Next.js 16.2.11、React 19.2.4、TypeScript 5.9.3 等相容的精确版本。

## 数据与运行方式

浏览器端继续采用本地优先结构：Zustand 管理运行状态，Dexie/IndexedDB 保存本机数据，`public/static-cloud-state.json` 提供共享静态初始状态。服务端 API 继续负责远端开奖同步和云状态访问。

恢复配置不得改写现有静态状态文件。缺失的样例 JSON 应从旧仓库恢复；若旧仓库不存在对应文件，再从现有静态状态中按源码要求生成，并通过种子与解析测试验证结构。

## 发布设计

### GitHub Pages

- GitHub Actions 在源码仓库的干净环境中安装锁定依赖、运行必要检查并验证 `out` 可生成。
- 静态导出临时禁用服务端 API 路由，使用仓库名作为 base path。
- 经本地发布脚本验证后，将 `out` 推送到既有 `rulequant-terminal-pages` 静态仓库；源码仓库不提交生成的 `out`。
- Pages 版本使用静态状态和浏览器端能力；依赖服务端 API 的功能应显示明确的降级或不可用状态。

### Vercel

- Vercel 连接同一 GitHub 仓库的默认分支。
- 使用标准 Next.js 构建，保留 API 路由和服务端同步能力。
- 数据库、GitHub 写入令牌、定时任务密钥和管理令牌只放在 Vercel 环境变量中。
- 发布前验证主要页面、API 可用性及静态状态加载。

## 公开仓库与安全边界

`.gitignore` 至少排除 `node_modules`、`.next`、`out`、`output`、浏览器配置、日志、临时发布目录、本地数据库和所有真实环境变量文件。

客户端 `NEXT_PUBLIC_*` 值会进入公开前端代码，不能保存真正的秘密。当前默认访问口令只能作为轻量提示门；如果网站需要真正的私有访问控制，应在 Vercel 服务端或平台访问控制层实现。恢复时移除源码中的真实默认口令，改为显式环境配置或关闭该门禁。

## 错误处理与回退

- GitHub 身份或仓库无法确认时，停止远端写入，但可继续重建本地环境。
- 远端与迁移源码冲突时生成差异清单，不自动覆盖业务文件。
- 依赖安装失败时保留锁文件与日志，先解决版本或网络问题，不删除业务数据。
- GitHub Pages 静态导出失败时不影响 Vercel 配置，反之亦然。
- 任何发布验证失败都阻止推送生产发布步骤。

## 验证标准

本地恢复只有在以下项目得到新鲜验证后才算完成：

1. 干净安装依赖成功。
2. 全部现有 Vitest 测试通过。
3. TypeScript 类型检查通过。
4. Next.js 生产构建通过。
5. 静态导出生成全部 18 个页面及静态状态文件。
6. 本地启动后关键页面可以访问。
7. `git status` 不包含依赖、缓存、浏览器配置或密钥文件。

发布只有在 GitHub Actions Pages 工作流成功、Pages 站点可访问、Vercel 生产部署成功且关键页面检查通过后才算完成。

## 实施顺序

1. 安装并连接 GitHub CLI，定位旧仓库。
2. 恢复 Git 历史和根目录配置，完成差异核对。
3. 补齐安全忽略规则、环境变量示例和缺失数据。
4. 清洁安装依赖并修复环境级问题。
5. 依次运行测试、类型检查、生产构建和静态导出。
6. 恢复 GitHub Pages 工作流与 Vercel 配置。
7. 用户确认远端目标后再提交和推送。
